# Урок 7. Поток в обе стороны: ScorePayments

## Зачем

Платёжный шлюз в час пик получает тысячи платежей подряд. Ждать конца пачки нельзя — каждому
покупателю ответ нужен сразу. **Поток в обе стороны** (bidirectional streaming): клиент шлёт
платежи один за другим, сервер отвечает на каждый **как только оценил**, не дожидаясь остальных.
Это живой диалог по одному соединению.

`ScorePayments` (BR-FRD-09):
- один ответ на каждый платёж, **в том же порядке**, с тем же `transaction_id` — по нему клиент
  сопоставляет ответы с запросами;
- поток ответов заканчивается, как только клиент закончил отправку;
- платёж с неверной суммой → `INVALID_ARGUMENT` с номером; ответы, которые уже пришли, остаются
  в силе.

Отличие от `CheckBatch`: там один итог в конце, здесь ответ на каждый платёж сразу.

## Попробуй в Postman

1. `ScorePayments`, metadata `x-api-key: dev-wallet-key`, **Invoke**.
2. Отправь платёж — ответ приходит **сразу**. Подожди, отправь второй (`GAMBLING`) — снова ответ.
3. **End streaming** → вызов закрывается со статусом `OK`.
4. Отправь платёж с `"amount": "abc"` → вызов завершается ошибкой `INVALID_ARGUMENT`.

## Посмотри в коде

```python
answers = stub.ScorePayments(iter(requests), metadata=WALLET, timeout=3)
first = next(answers)    # читаем по одному
```

Тест, который доказывает, что это настоящий поток, а не пачка:
`tests/grpc/test_bidi_streaming.py::test_answer_arrives_before_next_request` — клиент держит
второй платёж, пока не получит ответ на первый.

Сервер (`server.py`) — три строки:

```python
def ScorePayments(self, request_iterator, context):
    for index, request in enumerate(request_iterator):
        yield self.decide(request, context, index)
```

## Вопросы с собеседования

1. Чем bidirectional streaming отличается от client streaming?
2. Как сопоставить ответы с запросами в двустороннем потоке?
3. Почему тест двустороннего потока обязательно должен иметь дедлайн?

### Ответы

1. В client streaming один ответ в конце; в bidi ответы идут параллельно с запросами.
2. По идентификатору в ответе (`transaction_id`) или по договорённости о порядке; у нас есть оба.
3. Если сервер не закроет поток (как в BUG-18), тест без дедлайна повиснет навсегда; с дедлайном —
   упадёт и покажет баг.
