# Урок 5. Поток от сервера: WatchRiskEvents

## Зачем

Представь дежурного аналитика антифрода. Ему нужно видеть рискованные платежи **сразу**, а не
обновлять страницу каждую секунду. Для этого есть **поток от сервера** (server streaming):
клиент отправляет один запрос «подпиши меня», а сервер присылает сообщения по мере появления —
сколько угодно долго.

`WatchRiskEvents` (BR-FRD-07):
- запрос: `min_risk_score` — показывать только события с риском не ниже (0 = все; вне 0–100 →
  `INVALID_ARGUMENT`);
- ответ: поток `RiskEvent` — платёж, решение, риск, время, `request_id`;
- приходят только решения, принятые **после** подписки;
- поток идёт, пока клиент не отменит (`CANCELLED`) или не выйдет дедлайн (`DEADLINE_EXCEEDED`);
- одновременно не больше **8** подписчиков, девятый получит `RESOURCE_EXHAUSTED`. Каждый
  открытый поток держит рабочий поток (thread) сервера, пока не закончится. Без лимитов
  несколько забытых вкладок Postman заняли бы все потоки — и оплаты на сайте начали бы падать
  с 503. Такой баг нашёл ревьюер этого проекта; теперь есть лимиты и тест
  `tests/grpc/test_limits.py`.

Сразу после подписки сервер присылает начальную metadata `x-subscribed: true` — по ней клиент
понимает, что подписка уже действует.

## Попробуй в Postman

1. Вкладка 1: `WatchRiskEvents`, metadata `x-api-key: dev-monitor-key` (мониторингу смотреть можно),
   сообщение `{"min_risk_score": 0}`, **Invoke**. Вызов не заканчивается — это нормально.
2. Открой **сайт кошелька** (localhost:3000) и заплати картой. В Postman появится событие
   с твоим платежом. Заплати в категории `GAMBLING` — придёт событие с риском 80.
3. Перезапусти подписку с `{"min_risk_score": 50}` и снова заплати в обычном магазине —
   событие не придёт, потому что его риск 10.
4. Нажми **Cancel** / **End** — поток закрыт.

Это и есть связь gRPC с нашим сайтом: каждая оплата на сайте → REST в кошелёк → gRPC в антифрод →
событие в потоке.

## Посмотри в коде

```python
watch = Watch(stub)                                   # подписались (ждёт x-subscribed)
stub.CheckPayment(request, metadata=WALLET, timeout=2)
event = watch.find(request.transaction_id)            # ищем своё событие до 2 секунд
watch.stop()                                          # отписались
```

- `grpc-lab/lab.py`, класс `Watch`: читает поток в отдельном потоке выполнения (thread), потому что
  чтение потока «блокирует» — ждёт следующего сообщения.
- Сервер: `server.py` → `WatchRiskEvents`, хаб событий — `fraud_service/events.py`.
- Сквозной тест «оплата через REST → событие в gRPC»: `tests/integration/test_risk_stream.py`.

## Вопросы с собеседования

1. Когда выбрать server streaming вместо опроса (polling)?
2. Как протестировать бесконечный поток?
3. Что проверить при обрыве подписки?

### Ответы

1. Когда события редкие и нужны сразу: поток не тратит запросы впустую и даёт событие без
   задержки.
2. Всегда с дедлайном или отменой; проверять, что нужное событие пришло за разумное время, что
   фильтр работает, что поток завершается ожидаемым кодом.
3. Что сервер освобождает ресурсы: после отмены 8 подписчиков новые снова подключаются
   (`tests/grpc/test_server_streaming.py::test_cancelled_watchers_free_their_slots`).
