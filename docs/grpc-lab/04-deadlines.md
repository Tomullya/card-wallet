# Урок 4. Дедлайны и отмена

## Зачем

Кошелёк не может ждать антифрод вечно: клиент стоит у кассы. Поэтому кошелёк даёт антифроду
**2 секунды**. Не успел — платёж не проводим, отвечаем `503` (BR-PAY-08).

В gRPC это называется **дедлайн** (deadline): «ответь до такого-то момента». Важно:
- дедлайн ставит **клиент**, не сервер;
- когда время вышло, клиент получает `DEADLINE_EXCEEDED`, а сервер видит, что вызов больше не
  активен, и может прекратить работу;
- вызов без дедлайна может висеть бесконечно — поэтому в тестах **всегда** `timeout=...`.

**Отмена** (cancel) — клиент сам кладёт трубку раньше дедлайна. Сервер получает сигнал,
клиент — код `CANCELLED`. Для потоков это обычное завершение: «больше не нужно».

Тестовый магазин `TEST_TIMEOUT` отвечает через 5 секунд (BR-FRD-02):

| Дедлайн клиента | Итог |
|---|---|
| 1 с | `DEADLINE_EXCEEDED` через ~1 с |
| 2 с (как у кошелька) | `DEADLINE_EXCEEDED`, кошелёк отвечает 503 |
| 7 с | `OK` через ~5 с |

## Попробуй в Postman

1. `CheckPayment` с `"merchant_name": "TEST_TIMEOUT"`. Найди в настройках запроса тайм-аут
   (если в твоей версии он есть) и поставь 1000 мс → `DEADLINE_EXCEEDED`. Без тайм-аута дождёшься
   ответа через 5 секунд.
2. Через Swagger кошелька заплати в магазине `TEST_TIMEOUT` → `503 FRAUD_SERVICE_UNAVAILABLE`,
   баланс не изменился. Это дедлайн 2 секунды в действии.
3. `WatchRiskEvents` (урок 5): запусти поток и нажми **Cancel** / **End** — поток закрыт тобой.

## Посмотри в коде

```python
stub.CheckPayment(payment(merchant_name="TEST_TIMEOUT"), metadata=WALLET, timeout=1)
# → grpc.RpcError с кодом DEADLINE_EXCEEDED

watch = Watch(stub, seconds=5)   # подписка на поток с дедлайном 5 с
watch.stop()                     # call.cancel() → CANCELLED
```

Кошелёк: `wallet-api/app/fraud_client.py`, `timeout=self._timeout` (2 секунды из настроек).

## Вопросы с собеседования

1. Кто задаёт дедлайн в gRPC?
2. Что будет, если не задать дедлайн?
3. Как протестировать поведение системы при медленном зависимом сервисе?

### Ответы

1. Клиент. Сервер узнаёт оставшееся время из вызова и может передать его дальше (распространение
   дедлайна по цепочке сервисов).
2. Вызов может висеть бесконечно, занимая ресурсы; в тестах — повиснет весь прогон.
3. Подменить зависимость медленной (у нас — магазин `TEST_TIMEOUT`), проверить код ошибки,
   время ответа и что данные не изменились (нет списания, нет записи).
