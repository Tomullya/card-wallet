# Урок 0. Основы gRPC

## Зачем

Когда ты платишь картой на сайте кошелька, кошелёк за долю секунды спрашивает антифрод:
«Пропускать платёж?». Это разговор **сервиса с сервисом**, человека тут нет. Для таких разговоров
банки и большие компании часто берут **gRPC** вместо REST: он быстрее, строже и умеет потоки.

## Три кирпича gRPC

**1. Контракт — proto-файл.** Открой `proto/fraudpb/fraud.proto`. Там написано:
- какие есть **методы** (`rpc CheckPayment(...) returns (...)`);
- какие **сообщения** они принимают и возвращают (`message CheckPaymentRequest { ... }`).

Клиент и сервер оба генерируют код из этого файла (`scripts/gen_proto.sh`), поэтому не могут
«разойтись» в названиях полей. В REST контракт — это документация (OpenAPI), которую можно не
соблюдать; в gRPC контракт — это код.

**2. Формат — protobuf.** REST шлёт текст JSON: `{"amount": "10.00"}`. gRPC шлёт **бинарные**
байты: вместо имени поля — его **номер** из proto (`string amount = 4;` → поле №4). Поэтому:
- сообщения меньше и разбираются быстрее;
- **номера полей нельзя менять** — старый клиент прочитает поле №4 как сумму, даже если ты его
  переименуешь. Новые поля добавляют с новыми номерами (так мы добавили `transaction_id = 4` в ответ).

**3. Транспорт — HTTP/2.** Одно соединение держит много вызовов одновременно, и данные могут
идти **потоком** в обе стороны. Отсюда четыре типа вызовов:

| Тип | Как в жизни | Наш метод |
|---|---|---|
| Обычный (unary) | вопрос — ответ | `CheckPayment`, `GetDecision` |
| Поток от сервера | подписка на новости | `WatchRiskEvents` |
| Поток от клиента | сдать пачку документов, получить одну квитанцию | `CheckBatch` |
| Поток в обе стороны | живой диалог | `ScorePayments` |

## gRPC против REST

| | REST | gRPC |
|---|---|---|
| Формат | JSON, текст | protobuf, байты |
| Контракт | OpenAPI, по желанию | proto, обязателен |
| Ошибки | HTTP-коды: 404, 500… | свои статус-коды: `NOT_FOUND`, `INTERNAL`… |
| Заголовки | headers | metadata (+ trailers в конце) |
| Потоки | нет (нужны WebSocket и т. п.) | встроены |
| Кто использует | браузеры, внешние клиенты | сервисы внутри компании |

В нашем проекте есть оба: сайт и Postman говорят с кошельком по **REST**, кошелёк с антифродом —
по **gRPC**.

## Попробуй в Postman

1. **New → gRPC**. В поле адреса: `localhost:50051`.
2. Открой список методов → выбери **Using server reflection** (или похожий пункт): Postman сам
   спросит у сервиса, какие методы есть. Это называется **reflection**.
3. Посмотри список: пять методов `fraud.v1.FraudService/...`. Пока ничего не вызывай —
   это в уроке 1.

## Вопросы с собеседования

1. Чем gRPC отличается от REST?
2. Что такое protobuf и почему нельзя менять номера полей?
3. Какие четыре типа вызовов есть в gRPC?
4. Почему gRPC редко используют прямо из браузера?

### Ответы

1. Бинарный protobuf вместо JSON, обязательный контракт в proto, HTTP/2 и встроенные потоки,
   свои статус-коды. REST — для внешних клиентов, gRPC — обычно между сервисами.
2. Формат сериализации по контракту. На проводе вместо имён полей — номера; сменишь номер —
   старые клиенты прочитают не то поле.
3. Unary, server streaming, client streaming, bidirectional streaming.
4. Браузеры не дают управлять HTTP/2 так, как нужно gRPC; нужен прокси gRPC-Web. Поэтому наш
   сайт ходит в REST, а gRPC — внутри.
