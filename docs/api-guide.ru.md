# Гайд по API — Mini Card Wallet

Подробное описание каждого эндпоинта: что он делает, какие параметры принимает, что обязательно, что нет и **почему так сделано**. Ссылки вида `BR-PAY-03` ведут к бизнес-требованиям в [`docs/requirements/`](requirements/README.md).

- Базовый адрес: `http://localhost:8000/api/v1`
- Интерактивная документация (Swagger): http://localhost:8000/docs
- Коллекция Postman: «Card Wallet API» + окружение «Card Wallet — local» (`postman/`)

---

## 0. Общие правила (действуют для всех эндпоинтов)

### Авторизация
Все эндпоинты, кроме `health`, `auth/register` и `auth/login`, требуют токен:

```
Authorization: Bearer <access_token>
```

- Токен выдаёт `POST /auth/login`, живёт **60 минут**.
- Нет токена, он неверный, просрочен или пользователь не найден → `401 UNAUTHORIZED`.

> **Почему Bearer-токен (JWT), а не сессия:** API не хранит состояние входа на сервере, токен сам содержит id пользователя и срок действия. Так устроено большинство современных банковских API.

### Формат ошибок
Любая ошибка выглядит одинаково (NFR-03):

```json
{ "error": { "code": "CARD_BLOCKED", "message": "Card is blocked" } }
```

Для ошибок валидации (`422`) добавляется список полей:

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Request validation failed",
  "details": [ { "field": "amount", "problem": "Input should be greater than 0" } ] } }
```

> **Почему единый формат:** клиент (фронтенд, мобильное приложение, автотест) разбирает все ошибки одним кодом и опирается на поле `code`, а не на текст сообщения, который может меняться.

### Коды ответов

| Код | Когда |
|---|---|
| `200` | Успешное чтение или действие без создания объекта |
| `201` | Объект создан (пользователь, счёт, карта, операция) |
| `401` | Проблема с токеном или неверный логин/пароль |
| `404` | Объект не найден **или принадлежит другому клиенту** |
| `409` | Конфликт с текущим состоянием (дубликат, лимит, повтор ключа) |
| `422` | Ошибка в данных запроса |
| `503` | Антифрод-сервис недоступен |

> **Почему чужой объект даёт `404`, а не `403`:** ответ `403 Forbidden` подсказал бы злоумышленнику, что объект с таким id существует. С `404` нельзя отличить «чужое» от «несуществующего». Это защита от IDOR (перебора чужих id).

### Деньги
- Суммы в ответах — **строки** с двумя знаками: `"100.00"`.
- В запросах можно прислать строку (`"10.50"`) или число (`10.5`), но не `true`/`false`.
- Не больше 2 знаков после точки: `"10.555"` → `422`.

> **Почему строки:** числа с плавающей точкой (`float`) теряют точность: `0.1 + 0.2 = 0.30000000000000004`. В финтехе за такое списывают лишнюю копейку. Строку клиент передаёт в десятичный тип без потерь (NFR-01).

### Время
Все даты в UTC, формат ISO 8601 с `Z`: `"2026-11-08T13:06:26.123Z"` (NFR-02).

### Идентификаторы
Все `id` — UUID (`"3f1c…-…"`). Если в пути не UUID (`/accounts/abc`) → `422`.

### Текстовые поля
Нулевой символ `\u0000` в любом текстовом поле → `422` (PostgreSQL не умеет его хранить).

## 1. Служебные

### `GET /health` — проверка, что всё работает

| | |
|---|---|
| Авторизация | Не нужна |
| Параметры | Нет |
| Ответ | `200` всегда |

```json
{ "status": "ok", "database": "ok", "fraud_service": "ok" }
```

- `status` = `"degraded"`, если база или антифрод недоступны (у соответствующего поля будет `"error"`).

> **Почему всегда `200`:** эндпоинт отвечает на вопрос «жив ли сам Wallet API», а состояние зависимостей передаёт в теле. Так мониторинг отличает «упал сервис» от «упала база».

## 2. Регистрация и вход (BR-AUTH)

### `POST /auth/register` — регистрация клиента

| | |
|---|---|
| Авторизация | Не нужна |
| Успех | `201` |

**Тело запроса:**

| Поле | Обязательно | Правила | Почему |
|---|---|---|---|
| `email` | Да | Корректный email; сохраняется в нижнем регистре, пробелы по краям убираются; уникальный | `Anna@Mail.com` и `anna@mail.com` — один человек, иначе можно завести два аккаунта на один ящик |
| `name` | Да | 1–100 символов после обрезки пробелов; не только пробелы | Имя показывается в интерфейсе, пустое или из пробелов бессмысленно |
| `password` | Да | Минимум 8 символов, хотя бы одна буква и одна цифра; максимум 72 **байта** | Минимальная сложность пароля; 72 байта — технический предел алгоритма bcrypt (кириллица занимает 2 байта на символ) |

```json
{ "email": "anna@example.com", "name": "Anna", "password": "Passw0rd1" }
```

**Ответ `201`:**
```json
{ "id": "…", "email": "anna@example.com", "name": "Anna", "created_at": "2026-11-08T13:00:00Z" }
```

| Ошибка | Когда |
|---|---|
| `409 EMAIL_ALREADY_REGISTERED` | Email уже занят (без учёта регистра) |
| `422 VALIDATION_ERROR` | Нарушено любое правило выше |

> **Почему пароль не возвращается:** ни пароль, ни его хеш никогда не покидают сервер (BR-AUTH-05). Пароль хранится только как bcrypt-хеш.

### `POST /auth/login` — вход, получение токена

| | |
|---|---|
| Авторизация | Не нужна |
| Успех | `200` |

| Поле | Обязательно | Правила |
|---|---|---|
| `email` | Да | Регистр и пробелы по краям не важны |
| `password` | Да | Строка |

**Ответ `200`:**
```json
{ "access_token": "eyJhbGciOi…", "token_type": "bearer", "expires_in": 3600 }
```

| Ошибка | Когда |
|---|---|
| `401 INVALID_CREDENTIALS` | Неверный email **или** неверный пароль — ответ одинаковый |

> **Почему одинаковый ответ на «нет такого email» и «неверный пароль»:** иначе злоумышленник мог бы проверять, какие email зарегистрированы. По той же причине время ответа в обоих случаях одинаковое.

### `GET /me` — кто я

| | |
|---|---|
| Авторизация | Да |
| Параметры | Нет |
| Ответ | `200` — `{id, email, name, created_at}` владельца токена |

> Удобно для проверки, что токен рабочий, и для отображения профиля во фронтенде.

## 3. Счета (BR-ACC)

### `POST /accounts` — открыть счёт

| Поле | Обязательно | Правила | Почему |
|---|---|---|---|
| `currency` | Да | Ровно `EUR`, `USD` или `PLN` (заглавными) | Счёт всегда в одной валюте; список ограничен, конвертации нет |

```json
{ "currency": "EUR" }
```

**Ответ `201`:**
```json
{ "id": "…", "currency": "EUR", "balance": "0.00", "created_at": "…" }
```

| Ошибка | Когда |
|---|---|
| `409 ACCOUNT_ALREADY_EXISTS` | У клиента уже есть счёт в этой валюте |
| `422` | Неизвестная валюта, `"eur"` маленькими, пустое значение |

> **Почему один счёт на валюту:** так проще клиенту (не нужно выбирать «какой из двух EUR-счетов») и проще контролировать баланс. Ограничение защищено и в базе (уникальный ключ `user_id + currency`).

### `GET /accounts` — список своих счетов
Без параметров. Возвращает **только счета владельца токена**, по дате создания.

### `GET /accounts/{account_id}` — один счёт с балансом

| Параметр | Где | Обязательно |
|---|---|---|
| `account_id` | Путь | Да, UUID |

Ответ — как при создании. Чужой или несуществующий счёт → `404 NOT_FOUND`.

### `POST /accounts/{account_id}/top-up` — пополнение

| Поле | Обязательно | Правила | Почему |
|---|---|---|---|
| `amount` | Да | `> 0` и `≤ 10000.00`, не больше 2 знаков после точки | Ограничение суммы одной операции — типичное правило для пополнений (защита от ошибок и отмывания) |

Валюту передавать **не нужно**: пополнение всегда в валюте счёта.

```json
{ "amount": "100.00" }
```

**Ответ `201`:**
```json
{
  "transaction": { "id": "…", "type": "TOP_UP", "amount": "100.00", "currency": "EUR",
                   "status": "APPROVED", "decline_reason": null, "merchant_name": null,
                   "card_last4": null, "created_at": "…" },
  "balance": "100.00"
}
```

| Ошибка | Когда |
|---|---|
| `404` | Чужой или несуществующий счёт |
| `422` | `0`, отрицательная сумма, больше `10000.00`, `10.555`, текст, `true` |

> **Граничные значения для тестов:** `0.01` и `10000.00` проходят; `0`, `0.00`, `10000.01` — нет.

## 4. Карты (BR-CARD)

### `POST /accounts/{account_id}/cards` — выпустить карту

| Поле | Обязательно | По умолчанию | Правила | Почему |
|---|---|---|---|---|
| `daily_limit` | Нет | `1000.00` | От `1.00` до `10000.00` | Клиент может сам ограничить траты по карте; максимум равен максимальной сумме платежа, чтобы крупные платежи доходили до проверки антифрода |

Тело можно отправить пустым: `{}`.

**Ответ `201` — единственный раз, когда видны полный номер и CVV:**
```json
{
  "id": "…", "account_id": "…",
  "pan": "4000001234567890", "cvv": "123",
  "expiry": "11/29", "status": "ACTIVE", "daily_limit": "1000.00"
}
```

- `pan` — 16 цифр, начинается с вымышленного `400000`, проходит проверку по алгоритму Луна.
- `expiry` — последний день месяца через 3 года (`MM/YY`).

| Ошибка | Когда |
|---|---|
| `404` | Чужой или несуществующий счёт |
| `409 CARD_LIMIT_REACHED` | На счёте уже 3 активные карты (заблокированные и истёкшие не считаются) |
| `422` | Лимит вне диапазона |

> **Почему номер и CVV показываются один раз:** так работают виртуальные карты в реальных банках. Сервер хранит только последние 4 цифры, ключевой хеш номера (для проверки уникальности) и bcrypt-хеш CVV. Восстановить их из базы нельзя (NFR-04).

### `GET /accounts/{account_id}/cards` — карты счёта
Список карт в маскированном виде (как ниже).

### `GET /cards/{card_id}` — одна карта

**Ответ `200`:**
```json
{
  "id": "…", "account_id": "…",
  "masked_pan": "**** **** **** 7890",
  "expiry": "11/29", "status": "ACTIVE", "block_reason": null, "daily_limit": "1000.00"
}
```

| `status` | Значение |
|---|---|
| `ACTIVE` | Можно платить |
| `BLOCKED` | Заблокирована; причина в `block_reason` |
| `EXPIRED` | Срок истёк (рассчитывается по дате, не хранится) |

| `block_reason` | Значение |
|---|---|
| `BLOCKED_BY_CLIENT` | Клиент заблокировал сам |
| `TOO_MANY_FAILED_ATTEMPTS` | 3 неверных CVV подряд |

### `POST /cards/{card_id}/block` — заблокировать карту
Тело не нужно. Ответ `200` — карта со статусом `BLOCKED`.

| Ошибка | Когда |
|---|---|
| `404` | Чужая или несуществующая карта |
| `409 CARD_ALREADY_BLOCKED` | Карта уже заблокирована |

> **Почему нет разблокировки:** в первой версии это сознательно не входит в объём. В реальных банках разблокировка обычно требует дополнительной проверки личности.

## 5. Платежи (BR-PAY) — главный эндпоинт

### `POST /payments` — оплата картой в магазине

**Заголовок:**

| Заголовок | Обязательно | Правила | Почему |
|---|---|---|---|
| `Idempotency-Key` | Да | 8–64 символа, уникален для каждого нового платежа | Защита от двойного списания (см. ниже) |

**Тело:**

| Поле | Обязательно | Правила | Почему |
|---|---|---|---|
| `card_id` | Да | UUID своей карты | Какой картой платим |
| `cvv` | Да | Ровно 3 цифры | Подтверждение, что плательщик держит карту |
| `amount` | Да | `> 0`, `≤ 10000.00`, до 2 знаков | Как у пополнения |
| `merchant_name` | Да | 1–100 символов после обрезки пробелов | Название магазина видно в выписке |
| `merchant_category` | Да | `GROCERIES`, `ELECTRONICS`, `TRAVEL`, `RESTAURANTS`, `GAMBLING`, `OTHER` | Категория нужна антифроду (азартные игры запрещены) |

Валюта не передаётся: платёж всегда в валюте счёта карты.

```json
{
  "card_id": "…", "cvv": "123", "amount": "10.00",
  "merchant_name": "Coffee Shop", "merchant_category": "RESTAURANTS"
}
```

**Ответ `201` — и для одобренного, и для отклонённого платежа:**
```json
{
  "transaction_id": "…", "status": "APPROVED", "decline_reason": null,
  "amount": "10.00", "commission": "0.50", "currency": "EUR", "created_at": "…"
}
```

Отклонённый:
```json
{ "transaction_id": "…", "status": "DECLINED", "decline_reason": "INSUFFICIENT_FUNDS",
  "amount": "10.00", "commission": null, "currency": "EUR", "created_at": "…" }
```

> **Почему отказ — это `201`, а не `4xx`:** запрос корректный, и система **создала** запись об операции со статусом «отклонено». Так устроены реальные процессинги: отказ — нормальный бизнес-результат, он виден в выписке. Коды `4xx` остаются для ошибок самого запроса.

#### Порядок проверок (BR-PAY-02)
Проверки идут строго по порядку, первая неудачная определяет причину отказа:

| # | Проверка | `decline_reason` |
|---|---|---|
| 1 | Карта не заблокирована | `CARD_BLOCKED` |
| 2 | Карта не истекла | `CARD_EXPIRED` |
| 3 | CVV верный | `INVALID_CVV` |
| 4 | Баланс ≥ сумма + комиссия | `INSUFFICIENT_FUNDS` |
| 5 | Сегодняшние траты + сумма ≤ дневной лимит | `DAILY_LIMIT_EXCEEDED` |
| 6 | Антифрод одобрил | `FRAUD_HIGH_AMOUNT` (сумма > 5000.00), `FRAUD_BLOCKED_CATEGORY` (`GAMBLING`) |

> **Почему антифрод последним:** это вызов внешнего сервиса, он медленнее и «дороже» локальных проверок. Нет смысла спрашивать антифрод, если денег на счёте всё равно не хватает.

#### Комиссия (BR-PAY-03)
- 1% от суммы, округление до цента «половина вверх», **минимум 0.50**.
- Примеры: `10.00 → 0.50`, `100.00 → 1.00`, `123.45 → 1.23`, `150.50 → 1.51`.
- Списывается только при одобрении, отдельной операцией `COMMISSION`.

#### Дневной лимит (BR-PAY-04)
- Считается по карте за календарный день **по UTC** (с 00:00 UTC).
- Учитываются только одобренные платежи; комиссия **не** учитывается.
- Платёж, который доводит сумму ровно до лимита, проходит.

#### Неверный CVV (BR-CARD-06)
- Каждый неверный CVV → отказ `INVALID_CVV` и +1 к счётчику попыток.
- **3 неверных подряд** → карта блокируется (`TOO_MANY_FAILED_ATTEMPTS`).
- Успешный платёж обнуляет счётчик. Отказы по другим причинам его не меняют.

#### Идемпотентность (BR-PAY-07)
- Тот же `Idempotency-Key` + те же данные → тот же ответ, деньги **не** списываются повторно.
- Тот же ключ + другие данные (сумма, магазин…) → `409 IDEMPOTENCY_KEY_REUSED`.
- Ключи у каждого клиента свои: один и тот же ключ у двух клиентов не конфликтует.
- CVV в сравнение «те же данные» не входит (он нигде не сохраняется даже в виде хеша).

> **Зачем это нужно:** клиент отправил платёж, а связь оборвалась до ответа. Он не знает, прошёл платёж или нет, и повторяет запрос. Без ключа деньги списались бы дважды. С ключом сервер узнаёт повтор и возвращает прежний результат. Так работают Stripe, Adyen и большинство платёжных API.

#### Параллельные платежи (BR-PAY-09)
Два одновременных платежа с одного счёта никогда не уведут баланс в минус: на время платежа счёт блокируется в базе. Пример: баланс 100.00, два параллельных платежа по 60.00 → один одобрен, второй `INSUFFICIENT_FUNDS`.

#### Ошибки

| Ошибка | Когда |
|---|---|
| `404` | Чужая или несуществующая карта |
| `409 IDEMPOTENCY_KEY_REUSED` | Ключ уже использован с другими данными |
| `422` | Неверные поля, нет `Idempotency-Key`, ключ короче 8 или длиннее 64 |
| `503 FRAUD_SERVICE_UNAVAILABLE` | Антифрод не ответил за 2 секунды или вернул ошибку. **Ничего не сохраняется**, деньги не списаны, тот же ключ можно использовать повторно |

#### Тестовые магазины
| `merchant_name` | Что происходит |
|---|---|
| `TEST_TIMEOUT` | Антифрод отвечает через 5 секунд → `503` примерно через 2 секунды |
| `TEST_ERROR` | Антифрод возвращает ошибку → `503` |

## 6. Выписка (BR-STM)

### `GET /accounts/{account_id}/transactions` — история операций счёта

**Параметры строки запроса (все необязательные):**

| Параметр | По умолчанию | Правила | Зачем |
|---|---|---|---|
| `date_from` | — | `YYYY-MM-DD`, включительно | Начало периода |
| `date_to` | — | `YYYY-MM-DD`, включительно; не раньше `date_from` | Конец периода |
| `status` | — | `APPROVED` или `DECLINED` | Например, только отказы |
| `type` | — | `TOP_UP`, `PAYMENT`, `COMMISSION` | Например, только комиссии |
| `limit` | `20` | 1–100 | Сколько записей на странице |
| `offset` | `0` | ≥ 0 | Сколько записей пропустить |

Пример: `/accounts/{id}/transactions?status=DECLINED&limit=10&offset=0`

**Ответ `200`:**
```json
{
  "items": [
    { "id": "…", "type": "PAYMENT", "amount": "10.00", "currency": "EUR",
      "status": "APPROVED", "decline_reason": null, "merchant_name": "Coffee Shop",
      "card_last4": "7890", "created_at": "…" }
  ],
  "total": 3, "limit": 20, "offset": 0
}
```

- Сортировка: сначала новые.
- `total` — сколько всего операций подходит под фильтры (для постраничного вывода).
- `card_last4` есть только у карточных операций.

| Ошибка | Когда |
|---|---|
| `404` | Чужой или несуществующий счёт |
| `422` | Неверный формат даты, `date_from` позже `date_to`, неизвестный статус/тип, `limit` вне 1–100, отрицательный `offset` |

> **Почему постраничный вывод обязателен:** у реального клиента тысячи операций. Отдавать все разом — медленно и тяжело для мобильного приложения. `limit` ограничен 100, чтобы один запрос не мог «положить» сервер.

> **Проверка целостности (BR-STM-04):** баланс счёта всегда равен сумме одобренных пополнений минус одобренные платежи и комиссии. Это проверяет SQL-тест `tests/db/test_balance_consistency.py`.

## 7. gRPC: антифрод-сервис (BR-FRD)

Адрес: `localhost:50051`. Контракт: [`proto/fraudpb/fraud.proto`](../proto/fraudpb/fraud.proto). Вызывать напрямую нужно только для тестов — Wallet API делает это сам при каждом платеже.

### `fraud.v1.FraudService/CheckPayment`

**Запрос** (все поля — строки):

| Поле | Пример |
|---|---|
| `transaction_id` | UUID операции |
| `user_id` | UUID клиента |
| `card_last4` | `"7890"` |
| `amount` | `"123.45"` — строкой, чтобы не терять точность |
| `currency` | `"EUR"` |
| `merchant_name` | `"Coffee Shop"` |
| `merchant_category` | `"RESTAURANTS"` |

**Ответ:**

| Поле | Значения |
|---|---|
| `decision` | `APPROVE` или `DECLINE` |
| `reason` | `HIGH_AMOUNT`, `BLOCKED_CATEGORY` или пусто |
| `risk_score` | `10` (одобрено), `80` (азартные игры), `90` (крупная сумма) |

Правила по порядку: сумма > 5000.00 → `HIGH_AMOUNT`; категория `GAMBLING` → `BLOCKED_CATEGORY`; иначе `APPROVE`. Сумма ровно 5000.00 одобряется.

В ответе есть и `transaction_id` — копия из запроса.

**Как вызвать в Postman:** New → gRPC → `localhost:50051` → методы подтянутся через server reflection → выбрать `CheckPayment` → вкладка Metadata: `x-api-key: dev-wallet-key` → Use Example Message.

### Metadata: ключ доступа и ID запроса (BR-FRD-04, BR-FRD-05)

| Ключ | Обязателен | Смысл |
|---|---|---|
| `x-api-key` | да, для всех методов `FraudService` | `dev-wallet-key` — всё; `dev-monitor-key` — только `WatchRiskEvents` и `GetDecision` |
| `x-request-id` | нет | ID запроса; сервис возвращает его в trailers (или свой UUID) и пишет в лог |

Health check и reflection работают без ключа.

### Остальные методы

| Метод | Тип | Что делает |
|---|---|---|
| `GetDecision` | обычный | решение по `transaction_id`; неизвестный → `NOT_FOUND` |
| `WatchRiskEvents` | поток от сервера | живые события риска с фильтром `min_risk_score` (0–100); до 8 подписчиков |
| `CheckBatch` | поток от клиента | пачка до 1000 платежей → один итог `total / approved / declined`; ошибка в одном — отклоняется вся пачка |
| `ScorePayments` | поток в обе стороны | ответ на каждый платёж сразу, в том же порядке |

### Статус-коды

| Код | Когда |
|---|---|
| `INVALID_ARGUMENT` | сумма не число; `min_risk_score` вне 0–100; пустая пачка |
| `NOT_FOUND` | `GetDecision` с неизвестным id |
| `UNAUTHENTICATED` | нет ключа или ключ неизвестен |
| `PERMISSION_DENIED` | ключ мониторинга на методе, который ему нельзя |
| `RESOURCE_EXHAUSTED` | пачка больше 1000; 9-й подписчик потока |
| `DEADLINE_EXCEEDED` | клиент не дождался (магазин `TEST_TIMEOUT` отвечает 5 с) |
| `CANCELLED` | клиент сам отменил вызов |
| `INTERNAL` | магазин `TEST_ERROR` |
| `UNAVAILABLE` | сервис не запущен или неверный адрес |

Подробно, с упражнениями: [gRPC-тренажёр](grpc-lab/README.md).

> **Почему gRPC, а не REST:** это внутренний вызов между сервисами. gRPC быстрее (бинарный формат), а контракт строго описан в `.proto`-файле, из которого генерируется код для обеих сторон. Так обычно общаются сервисы внутри платёжной системы.

## Шпаргалка: сценарий «от регистрации до выписки»

1. `POST /auth/register` → `POST /auth/login` → сохранить токен
2. `POST /accounts` `{"currency":"EUR"}` → сохранить `id`
3. `POST /accounts/{id}/top-up` `{"amount":"100.00"}`
4. `POST /accounts/{id}/cards` `{}` → сохранить `id` карты и `cvv`
5. `POST /payments` с `Idempotency-Key` → `APPROVED`, баланс `89.50`
6. `GET /accounts/{id}/transactions` → три операции: пополнение, платёж, комиссия

В коллекции Postman шаги 1–6 сохраняют токен, `account_id`, `card_id` и CVV автоматически — запросы можно просто выполнять сверху вниз.
